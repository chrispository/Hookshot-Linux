# Ultrawide (43:18) — design and working notes

Goal: true Hor+ ultrawide for the Ocarina of Time (Switch 2) recomp on a 3440x1440 display
(3440/1440 = 43:18 = 21.5:9). `main` stays clean (upstream + the Linux PR); all of this work
happens on `ultrawide-43-18`.

## Where things stand today (upstream behavior)

- `gpu/render/rx_present_fx.cpp`, `present_rect()`: with Ultrawide **off** (the default) the
  16:9 frame is drawn centered into the black-cleared window at true scale — pillarbox.
  Correct, no distortion, what we ship first.
- With Ultrawide on, the frame is **stretched** over the window. The camera-patch hook that
  should widen the FOV first (`hos_ultrawide_apply`) is an **empty stub** in `host/mkw_glue.c`
  (marked "(totk_ultrawide.c)" — the TotK implementation was never ported). Result: the
  README's known symptom — 3D keeps its shape only by luck of the stretch, HUD stretches,
  picture softens.

So today's "Monitor's shape" is stretch-only. Our job: fill in what SkyboundTotk has.

## Prior art (the playbook)

1. **Presentation letterbox** — Ryujinx/yuzu/Eden "Aspect Ratio" option: render native,
   center, black-fill. Emulator-side 21:9 modes do *nothing* without game mods.
2. **Fruithapje21/TOTK-Ultrawide** — generates patched exefs/romfs for TotK: camera aspect
   patches + HUD fixes. Confirmed the approach is patch-game-code, not emulator.
3. **SkyboundTotk `a64-kit/hos/totk_ultrawide.c`** (same author as Hookshot) — the full
   recipe, in-process:
   - `SPLICE_AFTER` the lifted `fdiv` that computes camera `width/height`; overwrite the
     result register (`c->vreg[0]`) with `hos_view_aspect` when set.
   - `hos_ultrawide_apply()`: runtime-patch the stored 16:9 constant in guest memory
     (TotK: `main+0x377ac54`, bit pattern `0x3FE38E3B`, checked before writing).
   - HUD: at five `ldp s0, s1` UI-layout sites, multiply the horizontal scale by
     `aspect / (16:9)` so HUD keeps proportions after the present stretch.
   - Narrow windows (16:10, 4:3) work by the same mechanism inverted.
   - TotK 1.0.0 addresses: camera fdiv at `main+0x1968c2c` and `main+0x1e5eae8`; HUD `ldp`
     pairs at `+0x12ade68, +0x12ae24c, +0x1a8e69c, +0x1a8f18c, +0x1a93954`.

## Hookshot mechanism notes (verified in this repo)

- Lifted code lives in `work/sa/gen/code_*.c` (57 files, generated by `nx2/lift.py`).
- `host/hos.h` documents `ENTRY_HOOK(addr)` (function entry, can return 1 to replace the
  call) and `SPLICE_AFTER(addr, "anchor text")` (runs inside the lifted function right
  after the first lifted-C line containing the anchor text; `build.py` splices it in and
  **stops the build if the anchor is not found**; one per function; `SPLICE_AFTER_EACH`
  for every matching line).
- Existing OoT patches: `nx2/oot_patches.py` (applied by `lift.py` after writing the gen
  files). Pattern: literal text replacement in the gen C + an `extern volatile` runtime
  switch. Already contains a **dynamic-resolution patch** (`hos_fixed_resolution`,
  `hos_fixed_scale_bits`, config flag at `main+0x805BD0` / gen label `L_8082640c` in
  `code_007.c`) — the "Max Resolution" path that renders 3D at fixed full scale. Useful
  later for the softness problem.
- The Linux build compiles the POSIX branch of `mkw_glue.c` (`#else` at lines 704–762);
  that is where the `hos_ultrawide_apply` stub to replace lives. `hos_view_aspect` is
  already declared/consumed: `rx_present_fx.cpp` clamps it to 1.25–4.0 and stretches the
  present when it is > 0 — i.e. the renderer side is done; only the game-side hooks are
  missing.
- Float divides in gen code appear as `a64_fpx_div32_div32(c, a, b)` calls (float
  immediates are inlined as lowercase hex ULLs, e.g. `0x3f800000ULL`).

## Findings so far

- The game image (96 MB, base 0x80000000) contains two 16:9 floats inside `main`
  (0x80020000–0x84EC0000):
  - `0x3FE38E3B` at guest **0x83F15DCC** — the exact bit value TotK uses for its aspect
    constant. Strong candidate, but:
  - `0x3FE38E39` at guest **0x83E6131C** — the standard float rounding of 1.777778.
- **Neither is referenced by the lifted code** — no `adrp` page references
  (`0x83e61000`/`0x83f15000` produce zero gen hits) and no immediate forms
  (`3fe38e39`/`3fe38e3b` in any casing produce zero gen hits). So the camera aspect is most
  likely computed at runtime (`width/height`, as in TotK) and/or these data constants are
  reached through pointer indirection we can't see statically.
- `main` is stripped: 24,558 dynamic exports are all `nn::` SDK / allocator symbols
  (mii, irsensor, chat cameras...), nothing from the game engine. Symbol maps are a dead
  end; targeting must be by disassembly and runtime probing.
- The resolution manager around `L_8082640c` (`code_007.c`, patched by oot_patches.py) is
  the neighborhood where render-target scale is decided; camera aspect likely lives in
  viewport/projection setup nearby.

## Plan

1. **Camera aspect site(s)**: find the `a64_fpx_div32_div32` whose divisor+dividend are
   render width/height and whose result feeds the camera/projection. Approaches, in order
   of cost:
   - Static: disassemble around the projection-matrix builders (look for tan(fov/2)
     reciprocals and matrix stores near the div).
   - Runtime (probably decisive): add a temporary host log that samples div results ≈
     1.7778 per frame with backtraces (the recomp logs well; `sasym.py`/`samap.py`
     symbolize runs once a build exists).
2. **Stored constant**: once cameras are found, `hos_ultrawide_apply` patches
   `0x83F15DCC` (and/or `0x83E6131C`) with the same 0x3FE38E3B sanity check TotK uses.
3. **HUD sites**: find the UI layout scale loads (TotK pattern: `ldp s0, s1` pairs) and
   splice the `× aspect/(16:9)` multiplier onto the horizontal value. OoT HUD is simpler
   than TotK's (fixed elements: hearts, rupees, C-buttons, minimap) so there may be fewer
   sites.
4. **Softness**: with cameras widened, optionally force `hos_fixed_resolution` /
   `hos_fixed_scale_bits` so the 3D renders at full 43:18-backed scale instead of the
   dynamic-resolution budget. Measure GPU cost; the game was built for 4K/60 on Switch 2,
   so a desktop GPU should hold 1440p Hor+.
5. Wire-up: new `host/oot_ultrawide.c` (SPLICE_AFTERs + the real `hos_ultrawide_apply`),
   called from the `mkw_glue.c` POSIX branch (and the Windows branch kept building).
6. Test matrix: 3440x1440 window; pillarbox (regression), stretch (old behavior), full
   Hor+; HUD screenshots; Hyrule Field perf.

## Do we recompile to test?

Yes, but only incrementally, and that is cheap after the first build:

- The lift (gen C) is cached; `oot_patches.py` changes mean re-running the patch step, not
  a fresh lift.
- `build.py` has a content-hash object cache (`cache_put` hard-links objects); a host-file
  or single-gen-file change recompiles just those objects, then links. The shader
  translator stamp means shader caches survive unrelated changes.
- Runtime knobs (`RX_ULTRAWIDE`, `hookshot_options.ini`, `hos_fixed_scale_bits`) need no
  rebuild at all.

So the iteration loop for step 1–4 is: edit gen patch / hook → rebuild one object + link →
run. Minutes, not the ~40-minute first build.

## The renderer problem (discovered at first link)

The full present pipeline — letterboxing (`present_rect`), FSR, frame generation, the
F6–F10 hotkeys, and the only real consumer of `hos_view_aspect` — lives in
`gpu/render/rx_present_fx.cpp`, which `build.py` compiles **only when wgpu-native is
available** (`work/eg` layout: `webgpu.h` + `libwgpu_native.so`). The PR's Linux build
runs **without the renderer**: `host/linux/wgpu_stub.c` stubs the `wgr_*` surface, and the
Vulkan back end presents the game's frame straight into the swapchain. Consequences:

- No letterboxing: a 43:18 window shows the 16:9 frame **stretched**, not pillarboxed.
- No FSR / framegen / sharpness / in-window hotkeys; the Insert menu is Windows-only too
  (`vk_menu.cpp` is excluded from Linux builds by build.py).
- `hos_view_aspect` exists but nothing reads it.

Two ways forward, to decide after the first launch:

1. **Get wgpu-native on Linux** (download or build `libwgpu_native.so` matching
   `gpu/compat`'s `webgpu.h`; build.py looks under `work/eg` / `RX_CPM` / `WGPU_NATIVE`).
   Restores the whole present pipeline unchanged. Best if a compatible release exists.
2. **Port aspect-correct present into the Vulkan back end** (`gpu/vk/vk_replay.cpp`
   present path): compute `present_rect`'s centered-rect math at blit time and clear the
   bars. Also the natural home for the Hor+ stretch once cameras are patched — one
   renderer, no wgpu dependency. More work, fully under our control.

## Link fixes made on the way (Linux build bugs in PR #32)

- `vk_memory.cpp`: lambda return type deduction mixed `unsigned long long` with
  `uint64_t` (clang/Linux LP64); fixed with an explicit `-> uint64_t`.
- `nx2/build.py` + `scripts/build-linux.sh`: `libavformat` was missing from the FFmpeg
  pkg-config list, but `host/linux/movie_ff.c` calls libavformat's `av_read_frame`.
- `host/linux/wgpu_stub.c`: `rx_present_hotkey` was referenced by `display.c` but not
  stubbed; added (returns a "no renderer" notice).
